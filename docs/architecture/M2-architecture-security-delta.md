# M2 Architecture and Security Delta

## Architecture Direction

M2 preserves the frozen BOOT/M0/M1 dependency direction:

```text
curios_contracts
  <- curios_core
  <- cognitive / DAG / capability / persistence / runtime / providers
  <- DataLab bounded application/runtime surfaces
  <- FastAPI API
  <- web interface
```

Frameworks, data parsers, databases, model providers, UI libraries, and tools
remain implementation details. Curios contracts and recorded truth remain
canonical.

## DataLab Run Ownership And Direction

| Concern | Owner | Direction |
| --- | --- | --- |
| Canonical DataLab value contracts | `curios_contracts` | Consumed by runtime, persistence repositories, API, and web DTOs. |
| DataLab run lifecycle semantics | `curios_runtime` | Owns `DataLabRunState`, `DataLabRunRecord`, transitions, invariants, and repository behavior. |
| Durable storage representation | `curios_persistence` | Owns `PersistenceRecordKind`, table/schema/migration, transaction primitives, payload hash/version checks, and bounded storage errors. |
| API consumer | `apps/api` | Depends outward on runtime/repository surfaces and does not define run lifecycle semantics. |
| Web consumer | `apps/web` | Uses explicit DataLab API-boundary functions and does not own network or run semantics. |

`curios_persistence` may store a JSON-compatible payload for a DataLab run and
return primitive persistence records. It must not become the semantic source
for DataLab run states or transitions. The DataLab runtime repository must
reconstruct `curios_runtime.DataLabRunRecord` exactly from the persisted
representation or fail boundedly.

## New M2 Surface Categories

| Surface | Authority |
| --- | --- |
| DataLab contracts | Canonical only where existing BOOT/M1 contracts are insufficient. |
| DataLab dataset intake | Bounded local CSV upload validation and artifact metadata/reference creation. |
| DataLab decomposition | Deterministic planning for supported dataset-profiling objectives. |
| DataLab persistence | Run/result/evidence metadata, no raw dataset persistence by default. |
| DataLab profiler seam | In-process deterministic profiler boundary only. |
| DataLab profiler | Fixed deterministic CSV profiling behavior. |
| DataLab API | Exact bounded FastAPI operations. |
| DataLab web | Focused workspace using explicit API-boundary capabilities. |

## Prohibited Architecture Expansion

M2 does not authorize:

- generic application framework;
- general-purpose chat or assistant shell;
- arbitrary file manager;
- arbitrary tool/subprocess framework;
- network fetcher;
- model generation, chat, embeddings, or cloud model execution;
- production scheduler;
- autonomous agents;
- memory/knowledge runtime;
- project/session platform beyond durable DataLab run identity;
- release/deployment/tag authority.

## Security Authority Matrix

| Authority | M2 bound | Forbidden |
| --- | --- | --- |
| File read | Only staged/authorized dataset upload bytes for the active DataLab intake/run. | Arbitrary paths, parent traversal, home/workspace scanning, symlinks outside staging. |
| File write | Bounded DataLab result/evidence artifacts where explicitly authorized. | Arbitrary writes, source tree mutation, executable artifact creation. |
| Network | None for DataLab dataset/tool/model behavior. | Remote dataset fetch, cloud APIs, model network calls. |
| Tool execution | Deterministic in-process profiler only. | Shell, subprocess, plugin runner, external command execution. |
| Model invocation | None. | Ollama generation, chat, embeddings, cloud model credentials. |
| Persistence | Dataset metadata/reference/integrity plus DataLab run/result/evidence. | Raw dataset bytes by default, arbitrary object storage, project platform. |
| Frontend | Explicit DataLab API-boundary functions only. | Direct App `fetch`, WebSocket, EventSource, sendBeacon, generic request escape hatch. |
| CI | Deterministic local gates only. | Live model gates, deployment/release/publish steps. |

## Dataset Intake Security

- Accepted media is `text/csv`.
- Upload size is bounded to 1 MiB.
- Upload transport is raw request body, not multipart and not JSON base64.
- `X-Curios-Dataset-Filename` is required display metadata. It is normalized
  to NFC, then rejected if empty, longer than 128 Unicode scalar values,
  path-like, absolute, drive-qualified, containing `/`, `\`, `.`, `..`, NUL,
  or ASCII/C0/C1 control characters.
- Invalid filename metadata is rejected; it is not silently rewritten after
  normalization.
- The staged locator is generated by CuriosOS, opaque, provider-neutral, and
  confined to the authorized staging boundary.
- Parser must enforce UTF-8, header row, 10,000 data-row maximum, 100-column
  maximum, 16 KiB cell maximum, duplicate-column rejection, and empty-dataset
  rejection.
- Filename is display metadata only; path semantics are rejected.
- SHA-256 integrity is recorded before analysis.
- Raw parser/native exceptions must not cross API/web public boundaries.
- Secret-shaped locators or metadata fail boundedly or are redacted before
  evidence/result display.

## Dataset Lifetime

Raw dataset bytes are ephemeral staged input. They exist only from successful
intake through the terminal state of the owning DataLab run. Terminal cleanup
deletes or invalidates staged bytes. Cleanup failure is recorded as bounded
operational evidence and never upgrades the dataset reference into persistent
file authority. Restart before terminal completion requires the authorized
staging provider to prove the same bytes still exist and match SHA-256;
otherwise the run fails or defers with `DATASET_UNAVAILABLE`. Re-analysis
after cleanup requires a new upload.

## Tool Seam

Owner: DataLab runtime/profiler package introduced by `TASK-M2-006`.

Request:

- dataset `ArtifactReference(kind=dataset)`;
- authorized staged-input handle generated by CuriosOS;
- expected dataset SHA-256;
- profiling constraints and resource bounds;
- DataLab run ID and WorkItem reference;
- correlation/trace context following existing observability conventions.

Outcome:

- `Result` success/failure envelope;
- canonical `DatasetProfile`;
- bounded `DataLabFinding` values when profiling detects findings;
- `EventEnvelope` records for start, success, bounded failure, and timeout;
- `EvidenceReference` values bound to the same run, work, dataset reference,
  SHA-256, and result identity.

The seam permits deterministic in-process execution only. It forbids shell,
subprocess, arbitrary Python import execution, plugin loading, dynamic code,
network, external database, arbitrary filesystem traversal, and model
invocation. Cancellation and timeout produce fixed bounded outcomes and do not
emit raw exception text.

## Profiler Semantics

M2 profiling computes:

- dataset `row_count` and `column_count`;
- per-column name, index, inferred primitive type, `missing_count`,
  `non_missing_count`, and bounded `distinct_count`;
- for `INTEGER` and `DECIMAL` columns only: deterministic `minimum`,
  `maximum`, and `mean`;
- bounded warnings/findings for duplicate rejection, mixed types, empty
  columns, high missingness, and resource truncation.

Primitive type vocabulary is `STRING`, `INTEGER`, `DECIMAL`, `BOOLEAN`,
`EMPTY`, and `MIXED`.

Inference is deterministic and locale-independent:

- empty cells are missing;
- whitespace is trimmed for inference but original cell text is not persisted
  in profile output;
- boolean tokens are case-insensitive `true`, `false`, `yes`, `no`, `1`, `0`;
- integers match optional sign plus base-10 digits;
- decimals match optional sign plus base-10 decimal notation with `.` only;
- non-finite values such as `NaN` and `Infinity` are strings, not numbers;
- leading-zero integers remain integers and are not reserialized as raw
  original values;
- mixed non-missing primitive classes infer `MIXED`;
- all malformed or unsupported values are summarized boundedly, not echoed.

## DataLab Run State

M2 uses a minimal aggregate run lifecycle:

```text
CREATED -> READY -> RUNNING -> AWAITING_VERIFICATION -> COMPLETED
                         \-> FAILED
READY ---------------------> FAILED
AWAITING_VERIFICATION -----> FAILED
```

Terminal states are `COMPLETED` and `FAILED`. Reapplying the same transition
with the same evidence is idempotent. `COMPLETED` requires M1 verification
`APPROVED`. Verification `REJECTED` moves the run to `FAILED`.
Verification `DEFERRED` leaves the run in `AWAITING_VERIFICATION`. The run
state summarizes aggregate DataLab truth and does not replace Work DAG node
states.

## Verification Mapping

DataLab uses the existing M1 verification attempt vocabulary:

| Verification attempt | M1 completion decision | DataLab run effect |
| --- | --- | --- |
| `PASSED` | `APPROVED` | transition to `COMPLETED` |
| `FAILED` | `REJECTED` | transition to `FAILED` |
| `INCONCLUSIVE` | `DEFERRED` | remain `AWAITING_VERIFICATION` |
| `NOT_EVALUATED` | `DEFERRED` | remain `AWAITING_VERIFICATION` |
| zero attempts | `DEFERRED` | remain `AWAITING_VERIFICATION` |

The first terminal `PASSED` or `FAILED` attempt determines the terminal M1
completion decision. Later attempts cannot override that terminal result.
While the run remains `AWAITING_VERIFICATION`, a caller may explicitly submit a
new bounded verification request. This is not an automatic retry, scheduler
retry, executor retry, or hidden loop. Existing M1 `max_iterations` applies per
verification request.

Approval requires evidence bound to the correct WorkItem, DataLab run, dataset
`ArtifactReference`, dataset SHA-256, and profiler result/profile identity.
Wrong, stale, duplicate, wrong-run, wrong-work, or wrong-dataset evidence
cannot approve a run.

## API Failure Model

M2 API failures use one bounded envelope with:

- canonical `error_code`;
- safe fixed message class;
- `retryable`;
- request correlation/reference where safe;
- no raw request body, filename/header value, CSV cell contents, filesystem
  path, provider error, database error, traceback, or framework validation
  object.

Failure classes:

| Class | Meaning |
| --- | --- |
| Transport failure | Missing/unsupported/malformed media, malformed JSON, non-object JSON, oversized body, invalid filename/header, or malformed CSV transport. |
| Domain/contract failure | Valid transport but invalid DataLab request, reference, enum, capability, route, evidence, or run state. |
| Not found | Referenced dataset/run/work/evidence does not exist. |
| Conflict/stale state | Request is valid but conflicts with current run/version/state. |
| Internal bounded failure | Persistence, staging, profiler, or unexpected internal failure translated to fixed safe error. |

Domain outcomes such as `NO_ROUTE`, `ROUTE_NOT_EXECUTABLE`,
`AWAITING_VERIFICATION`, verification `DEFERRED`, and verification `REJECTED`
remain bounded domain responses when the request itself is valid. They are not
converted into generic transport failures.

## API And Web Authority

M2 API inventory is fixed by the milestone definition. The web app may call
only explicit API-boundary functions:

- `uploadDataLabDataset`;
- `createDataLabAnalysis`;
- `runDataLabAnalysisOnce`;
- `readDataLabRun`;
- `completeDataLabVerification`.

No generic method/path/body request function may be exposed to the App.

Web state has these provenance classes:

- `DRAFT`: selected local file metadata and objective draft;
- `ACCEPTED_CANONICAL`: accepted dataset reference and DataLab run;
- `RECORDED_RESULTS`: runner, profile, findings, events, evidence, and
  verification truth loaded from API/persistence;
- `TRANSIENT`: busy state and request generation;
- `ERROR`: bounded canonical failure.

Draft edits never mutate accepted canonical truth. Accepting a new dataset or
analysis invalidates downstream stale result and verification state. Failed
replacement preserves prior accepted truth.

Every M2 mutation/read action that can replace canonical UI state carries a
monotonic request generation for the canonical object it may update:

- `datasetGeneration`;
- `analysisGeneration`;
- `runGeneration`;
- `verificationGeneration`.

A response may update canonical UI state only when it belongs to the currently
active generation for that canonical object. Late responses from older
generations must not overwrite newer accepted canonical state, restore
invalidated downstream state, clear newer errors/status, or relabel a newer
dataset/run. Such responses may be discarded silently or recorded only as
bounded transient diagnostics.

Mutating actions are single-flight per action and canonical generation. UI
controls should be disabled while the corresponding action is active, but
generation rejection is the correctness mechanism and does not rely on disabled
buttons alone.

Dataset replacement:

- accepted dataset A remains canonical while draft dataset B is selected;
- successful B upload makes B canonical and invalidates A-derived analysis,
  run, profile, findings, and verification state;
- failed B upload preserves A and may keep B as draft with bounded error;
- late A-era upload responses cannot overwrite B.

Analysis replacement:

- accepted analysis A remains canonical while objective draft B is edited;
- successful B creation replaces A and invalidates stale run, profile,
  findings, and verification state from A;
- failed B creation preserves A with bounded error;
- late A-era create/run/verification responses cannot overwrite B truth.

Run-once and verification responses must bind to the current accepted
analysis/run generation and current result/evidence generation. If the
canonical dataset or analysis changes while a request is in flight, the old
response cannot update current canonical state.

## Safe Error Vocabulary

M2 public boundaries use bounded error codes for invalid media, oversized
upload, malformed CSV, invalid encoding, duplicate columns, empty dataset, too
many rows, too many columns, oversized cell, unsafe filename, missing staged
artifact, hash mismatch, profiler timeout, profiler failure, persistence
conflict/corruption, verification mismatch, and dataset unavailable. Raw
exception text, raw cell values, body/header echo, filesystem paths,
tracebacks, and framework diagnostics are not public error payloads.

## Policy Position

M2 may use frozen `PolicyDecision` and `EffectClassification` vocabulary to
record file/tool effects, but it does not implement a production IAM, RBAC,
ABAC, or approval workflow. `UNKNOWN` remains non-authorizing.

## Architecture Acceptance

M2 architecture/security validation must prove:

- no M2 component depends outward on FastAPI, React, database, or parser
  implementation details from canonical contracts;
- DataLab tool authority is not equivalent to a generic tool framework;
- no live model or network authority is introduced;
- frontend authority remains explicit and bounded;
- BOOT/M0/M1 guardrails remain active.
